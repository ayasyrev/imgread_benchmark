# Бенчмарк декодирования из memmap-кэша

Дата: 2026-09-04.
Статус: дизайн согласован в обсуждении; письменная спецификация подготовлена для ревью.

## Цель и сценарий использования

Добавить режим `--decode-only`: до начала замеров загрузить выбранные исходные
файлы изображений в переиспользуемый memmap-кэш на tmpfs, затем измерять
декодирование из этого кэша. Кэш содержит сжатые JPEG/PNG и другие исходные
файлы, а не декодированные пиксели.

Обычный быстрый запуск использует 200 изображений, более длинный — 2000–3000.
Пользователь переключается между двумя, иногда тремя вариантами датасетов.
Кэш сохраняется между запусками до вытеснения, ручного удаления или перезагрузки.
При увеличении выборки допускается пересборка кэша до начала замеров.

Проверенные текущие значения: CLI выбирает 200 изображений и делает 5 повторов;
Python API `BenchmarkImgRead` без ограничения выбирает все изображения.

Локальные размеры исходных файлов, измеренные 2026-09-04:

| Набор | Всего изображений | Весь набор, МиБ | Первые 200, МиБ | Первые 2000, МиБ | Первые 3000, МиБ |
| --- | ---: | ---: | ---: | ---: | ---: |
| `/Data/imagenette/imagenette2` | 13394 | 1496,01 | 23,69 | 233,54 | 353,39 |
| `/Data/imagenette/imagenette2-320` | 13394 | 332,17 | 5,36 | 51,24 | 74,75 |

Выборки соответствуют текущему порядку `get_img_filenames` при запуске от корня
каждого набора. Это измерения конкретных выборок, а не гарантированный размер
любых N файлов. Imagewoof локально не найден; его размер не используется для
расчёта лимита. Дублирующее содержимое проектной `.data` пользователь удалил.

## Интерфейс и совместимость

Новые параметры CLI:

- `--decode-only`: включить новый режим; по умолчанию выключен.
- `--cache-dir PATH`: корень кэша; по умолчанию
  `/dev/shm/imgread_benchmark-<uid>/`.
- `--cache-limit SIZE`: общий лимит кэша; по умолчанию `2GiB`.
  Принимает положительное целое число байтов или положительное целое с суффиксом
  `KiB`, `MiB`, `GiB`. Это верхняя граница, а не резервирование памяти.

Параметры `-n`, `-A`, `-r`, `-t`, `-l`, `-x`, `-m`, `--nw` сохраняют смысл.
Новые флаги работают как с явным подкомандным словом `benchmark`, так и при
автоматическом выборе этой подкоманды, в том числе перед путём к датасету.
Явные параметры кэша без `--decode-only` отклоняются с понятной ошибкой.

Пример:

```bash
uv run imgread_benchmark /Data/imagenette/imagenette2 \
  --decode-only -n 3000 -t np -r 5 --cache-limit 2GiB
```

В `BenchmarkImgRead` добавляются keyword-only параметры `decode_only=False`,
`cache_dir=None`, `cache_limit=2147483648` (байты). Кэш готовится при запуске
бенчмарка после выбора файлов и библиотек; конструктор не копирует датасет.
Переданный пользователем `func_dict` в decode-режиме должен содержать функции
декодирования из буфера по описанному ниже контракту.

Первая версия режима рассчитана на Linux и реально смонтированный tmpfs.
Другой путь разрешён через `--cache-dir`, но тоже проверяется на tmpfs.
При неподходящем окружении выдаётся ошибка; автоматического перехода на
дисковый кэш или обычное чтение нет. Обычный режим чтения продолжает работать
по существующим правилам, включая поддержку других платформ.

## Организация кэша

Каждый завершённый набор — отдельный неизменяемый каталог с двумя файлами:

- `data.bin`: последовательно записанные байты исходных файлов без дополнительного
  сжатия и без выравнивания каждого изображения до страницы памяти;
- `index.json`: версия формата кэша, идентификатор, суммарная длина данных,
  записи об исходных файлах и их диапазонах в `data.bin`.

Запись индекса содержит канонический абсолютный путь, `size`, `mtime_ns`,
`ctime_ns`, `offset` и `length`. Идентичность набора определяется версией формата
и нормализованным списком путей с этими исходными метаданными. Библиотека,
целевой формат, число повторов и число процессов в идентичность не входят.

Состав кэша и порядок выполнения разделены: один исходный файл хранится один
раз, а последовательность индексов сохраняет порядок и возможные повторы
переданного списка файлов. Сортировка для вычисления идентификатора не меняет
текущий порядок выборки бенчмарка.

Поиск сначала проверяет точное совпадение набора, затем подходящие надмножества.
Если все запрошенные файлы присутствуют и их метаданные совпадают, готовый кэш
используется повторно. Из нескольких подходящих выбирается наименьший.
Кандидат должен помещаться в текущий лимит; если большее надмножество не
помещается, допускается построить компактный кэш только запрошенной выборки.
Изменение файлов вне запрошенной выборки не мешает использованию её актуальных
записей. Переход с 3000 на 200 изображений не создаёт новую копию данных.

Если нужных записей нет или выбранные исходные файлы изменились, новый набор
строится целиком из текущей выборки. Пополнение существующего `data.bin` и
дедупликация данных между разными кэшами в первую версию не входят.

Проверка актуальности использует файловые метаданные и не перечитывает содержимое
исходных файлов при попадании в кэш. При сборке метаданные проверяются до и после
копирования каждого файла; обнаруженное изменение прерывает сборку. Датасет
предполагается неизменяемым на время подготовки и замеров. Это не механизм
обнаружения подмены содержимого с сохранением всех проверяемых метаданных.

## Сборка, лимиты и время жизни

1. Проверить выбранные файлы, объём данных, корень tmpfs и доступные декодеры.
2. Найти подходящий готовый кэш или спланировать место под новый.
3. При необходимости вытеснить давно не использованные неактивные наборы.
4. Последовательно скопировать исходные файлы во временный каталог сборки.
   Обычные файловые записи позволяют обработать нехватку места до создания
   отображения; весь датасет не собирается промежуточно в Python `bytes`.
5. Завершить индекс, проверить длину данных и границы диапазонов, затем
   атомарно переименовать каталог сборки в завершённый на том же tmpfs.
6. Открыть завершённые данные для чтения и держать аренду кэша до окончания
   работы использующих его процессов.

Корень кэша принадлежит текущему пользователю и создаётся с правами `0700`.
Служебные файлы блокировок и последнего использования находятся отдельно от
неизменяемых данных. Корневая блокировка сериализует поиск, сборку, публикацию
и вытеснение; уже запущенное декодирование не требует этой блокировки.
Каждый процесс, использующий набор, держит разделяемую блокировку этого набора.
Удаление требует неблокирующего получения исключительной блокировки: занятые
наборы пропускаются. Используются файловые блокировки, освобождаемые ОС при
завершении процесса, а не проверка одного сохранённого PID.

Общий лимит учитывает завершённые данные, индексы и временные сборки.
При планировании учитывается фактически выделенное место файлов; это не лимит
размера виртуальных отображений и не лимит памяти всего бенчмарка.
Вытеснение — LRU по последнему началу использования набора. Фиксированного
ограничения на два или три набора нет: сохраняются все помещающиеся наборы.
Новый явно уменьшенный лимит проверяется также при попадании в кэш: лишние
неактивные наборы вытесняются. Если используемые наборы не позволяют соблюсти
лимит текущего запуска, он завершается ошибкой, не прерывая другие запуски.

Перед новой сборкой дополнительно проверяются свободное место tmpfs и
`MemAvailable`. После ожидаемого выделения остаётся запас RAM не менее
`max(512 MiB, 10% доступного системе лимита RAM)` для декодеров и других процессов.
Лимит RAM — минимум `MemTotal` и обнаруженного конечного лимита cgroup.
Допустимое выделение ограничивается как `MemAvailable`, так и остатком cgroup,
если такой лимит существует.
Место после вытеснения проверяется заново. Это предварительная оценка:
конкурирующие выделения памяти могут изменить ситуацию после проверки.

Если новый набор не помещается даже после разрешённого вытеснения, запуск
заканчивается ошибкой с требуемым объёмом и причиной ограничения. Активный
набор не удаляется. Неактивная старая версия может быть вытеснена до сборки
новой, если одновременное хранение обеих не помещается.
При использовании уже готового кэша не резервируется его полный размер повторно.

Обычное завершение и исключения сначала освобождают представления буферов,
затем закрывают отображения и освобождают аренды,
сохраняя завершённый кэш. Незавершённые каталоги сборки удаляются при следующей
подготовке под корневой блокировкой. Повреждённый индекс, неверная длина данных
или выход диапазона за границы делают набор непригодным для использования.
Неактивный повреждённый набор удаляется и пересобирается; активный не изменяется,
а конфликтующий запуск получает диагностическую ошибку.

tmpfs очищается при перезагрузке. Предварительное обращение к страницам не
закрепляет их в RAM: при включённом swap и давлении на память tmpfs может
выгружаться. В этой версии нет управления swap или обязательного `mlock`.

## Контракт декодеров

Адаптер может предоставлять `decode_img(data)`, `decode_img_pil(data)` и
`decode_img_ndarray(data)` по аналогии с существующими `read_img*`.
`data` — непрерывный read-only `memoryview` исходного файла. Результат полностью
декодирован и имеет семантику соответствующего существующего целевого формата.
Для ленивого результата адаптер обязан завершить декодирование до возврата.

Адаптер создаёт необходимые `ndarray`, `bytes` или поток в памяти.
Эти преобразования входят в замер. Прямой доступ к буферу используется там,
где API библиотеки его поддерживает; нулевое копирование для всех библиотек
не является обещанием режима. Адаптер не открывает исходный файл и не заменяет
неподдерживаемую библиотеку другим декодером.

Первая реализация добавляет буферные адаптеры для Pillow, OpenCV, ajpegli,
imagecodecs, jpeg4py, simplejpeg, turbojpeg, imageio, skimage, imgread_rs и local_rs.
Наличие нужного API и работоспособность установленной версии проверяются;
опциональная зависимость не становится обязательной. У установленных
imgread_rs и local_rs обнаружены функции `from_bytes`.
Остальные существующие адаптеры участвуют в decode-режиме только после
добавления собственного буферного интерфейса; их текущие функции чтения по
пути не используются как замена. Внешние entry-point плагины могут предоставлять
тот же контракт без изменения ядра.

Реестр декодеров сохраняет ленивую загрузку библиотек. При выборе всех библиотек
неподдерживаемые комбинации библиотеки и целевого формата перечисляются как
пропущенные. Явный выбор неподдерживаемой библиотеки или отсутствие пригодных
декодеров завершаются ошибкой до сборки кэша.

Ошибки декодирования и результат `None` считаются неуспехом. Новый реестр не
применяет обёртку, которая превращает исключение в успешный пустой результат.
Численная скорость выводится только для библиотеки, обработавшей всю выбранную
последовательность во всех измеренных повторах.

## Граница измерения и multiprocessing

Измерение начинается с уже подготовленных представлений сжатых буферов и
заканчивается после получения и освобождения декодированных результатов всей
выборки. Внутри остаются вызовы адаптеров, необходимые преобразования входа и
целевого формата, обход последовательности и обработка результатов/ошибок.
Это время полного прохода декодирования через Python-адаптер, а не отдельно
измеренное время выполнения нативного кодека.

За пределами таймера находятся поиск файлов, проверка и сборка кэша, открытие
memmap, создание представлений диапазонов, импорт библиотек, предварительное
обращение к страницам, прогрев и вывод прогресса. Декодированные изображения
не кэшируются между вызовами и не накапливаются для всего датасета.

Для каждой библиотеки выполняется один неизмеряемый проход по всей выбранной
последовательности, затем указанное число измеренных повторов. Неуспех прогрева
помечает библиотеку как не обработавшую выборку; численные результаты для неё
не публикуются. После прогрева каждый повтор заново декодирует все изображения.

В последовательном режиме процесс один раз открывает кэш и заранее готовит
представления выбранных диапазонов. Перед прогревом обращается ко всем страницам
этих диапазонов. Прогресс измеренных повторов обновляется между повторами,
а не внутри цикла изображений.

При `-m` для каждой библиотеки создаётся пул до её замеров. Каждый worker
самостоятельно открывает тот же read-only memmap, держит аренду, готовит
представления и касается выбранных страниц. Каждый worker завершает импорт и
локальную инициализацию декодера с пробным декодированием до сигнала готовности.
После готовности всех worker выполняется полный неизмеряемый проход выборки;
тот же пул используется во всех измеренных повторах библиотеки и закрывается
после них. Поддержка не должна зависеть только от наследования памяти через fork.
Ошибка инициализации или завершение worker обнаруживаются родителем и приводят
к очистке пула и диагностике, а не к бесконечному ожиданию готовности.

В заданиях передаются номера изображений. Байты изображений и декодированные
массивы через очереди не передаются. Worker освобождает результат и возвращает
только статус либо описание ошибки с номером изображения. Передача заданий,
сбор статусов и синхронизация входят во время multiprocessing-прохода.
Вывод явно называет его пропускной способностью декодирования с multiprocessing.

## Структура реализации

- `encoded_cache.py`: индекс, сборка, проверка актуальности, выбор надмножества,
  лимит, LRU, блокировки и контекст владения read-only отображением.
- `decode_benchmark.py`: последовательные проходы, инициализация worker,
  прогрев, границы таймера и строгий учёт неуспехов.
- `img_libs/*.py` и `read_img.py`: буферные адаптеры и их ленивые реестры.
- `benchmark.py`: подключение нового режима к `BenchmarkImgRead`, выбор функций
  по целевому формату и сохранение существующего интерфейса результатов.
- `cli.py`: параметры, нормализация аргументов, сообщения о подготовке и режиме.

`benchmark_utils` сохраняет существующее поведение обычного режима. Новый
исполнитель не использует его цикл с обновлением прогресса на каждое изображение
и созданием пула внутри таймера. Результаты нового режима сохраняют секунды
на проход и изображения в секунду; ошибка одной библиотеки не мешает собрать
результаты других. При любой ошибке декодирования CLI возвращает ненулевой код
после вывода успешных результатов и сводки ошибок.

Перед замерами выводятся режим, число выбранных файлов, объём данных, попадание
в кэш или пересборка, путь к кэшу и вытесненные наборы. Время подготовки
показывается отдельно от результатов декодирования.

## Критерии приёмки

1. Первый запуск создаёт кэш; повторный и меньшая выборка используют его без
   чтения содержимого исходных файлов. Увеличение выборки создаёт новый набор.
2. Изменённый выбранный исходный файл вызывает пересборку. Порядок выполнения
   сохраняется при использовании кэша, построенного с другим порядком файлов.
3. Наборы сохраняются после выхода. LRU освобождает место только за счёт
   неактивных наборов; активный набор защищён также при отдельном втором запуске.
4. Прерванная сборка, повреждённый индекс и нехватка места не дают использовать
   частичные данные. Ошибки освобождают блокировки и отображения.
5. Для поддержанных форматов буферный и файловый адаптер одной библиотеки
   дают эквивалентный полностью декодированный результат. Между разными
   библиотеками побитовое равенство JPEG не требуется.
6. При повторном попадании в кэш после подготовки обращения к исходным файлам
   не нужны. Создание представлений, импорты, прогрев, запуск пула и обновления
   прогресса не попадают в измеряемый участок.
7. Последовательные и multiprocessing-проходы обрабатывают одинаковые файлы;
   проверяется запуск worker через spawn. Задания не содержат байты изображений.
8. Неуспешное декодирование или `None` не превращаются в хороший результат
   скорости. Явно неподдерживаемая библиотека отклоняется до сборки.
9. Обычный режим, текущие CLI-флаги, ленивые импорты и существующие плагины
   сохраняют работоспособность.

Проверки реализации выполняются через `uv run pytest` и `uv run ruff check`.
Тесты используют небольшие временные наборы; отдельная Linux-проверка выполняет
реальное чтение memmap на доступном tmpfs. Опциональные библиотеки проверяются
при наличии соответствующих зависимостей. Большие датасеты для тестов не
скачиваются, порог ускорения не используется как критерий корректности.

## Вне первой версии

Пополняемый кэш, дедупликация разных наборов, отдельная служба кэша, фоновое
вытеснение, кэш декодированных пикселей, GPU-замеры и изменение поведения
обычного файлового бенчмарка. Загрузка Imagewoof не является частью этой задачи.

## Источники технических ограничений

- [Документация Linux tmpfs](https://docs.kernel.org/filesystems/tmpfs.html):
  время жизни, учёт памяти и возможность swap.
- [Документация NumPy memmap](https://numpy.org/doc/stable/reference/generated/numpy.memmap.html):
  read-only отображения и совместное владение отображением представлениями.
- Текущие исходники `BenchmarkImgRead`, CLI, адаптеров и установленного
  `benchmark_utils`: измерение полного прохода, границы создания пула и прогресса.
