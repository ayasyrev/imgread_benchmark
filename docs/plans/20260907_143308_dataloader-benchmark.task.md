## Краткое описание

Добавить самостоятельный бенчмарк `torch.utils.data.DataLoader`, который читает один выбранный список изображений разными ридерами, выполняет общий опциональный пространственный трансформ и выдаёт батчи изображений с фиктивными таргетами `0`. Сравнивать время полного прохода и производительность на фактически выданное изображение при разных настройках DataLoader. По желанию пользователя одновременно наблюдать загрузку CPU и потребление памяти: быстрый вариант может иметь неожиданный расход ресурсов.

Это черновик постановки, а не план реализации. Пользователь уточнил контракт: один общий трансформ выполняет resize короткой стороны до 256 и центральный crop 224, выдаёт CPU Tensor `uint8 [0,255]` формы `3×224×224`. Масштабирование значений и нормализация исключены. Готовый RGB NumPy используется напрямую; PIL приводится к нему адаптером. Уточнение на вопрос пользователя о torchvision: уже готовый RGB CHW Tensor поступает напрямую в тот же общий трансформ, без промежуточного NumPy; оба входных представления сходятся перед одинаковой Tensor-геометрией.

## Проблема и свидетельства

Основной сценарий пользователя — последующий процессинг в PyTorch/torchvision. Время одиночного вызова декодера не включает всю подготовку и передачу готового батча в основной процесс. Результат нового бенчмарка должен относиться к конкретному пути подготовки и конфигурации, а не утверждать, какая библиотека быстрее при любых условиях.

Подтверждённые факты рабочего дерева `/home/aya/Prj/imgread_benchmark` на момент постановки, базовый commit `c0f450674620cc8119a73fc4222daf3bc84eb7e3`:

- `src/imgread_benchmark/get_img_filenames.py:get_img_filenames` рекурсивно собирает изображения и выбирает первые N; `0`/`None` означают все файлы. Порядок обхода не сортируется.
- `src/imgread_benchmark/benchmark.py:BenchmarkImgRead` измеряет чтение файлов с форматами `def/pil/np`, поддерживает повторы, shuffle и прогрев файлового кэша. Прогрев читает байты без декодирования, вне таймера.
- `src/imgread_benchmark/cli.py` содержит команды `benchmark`, `libs`, `data` и запуск старого бенчмарка по умолчанию. Его `--nw 0` означает все CPU.
- `src/imgread_benchmark/read_img.py` оборачивает некоторые ошибки чтения в предупреждение и `None`. В адаптерах `imgread_rs` и `local_rs` есть fallback. Их нельзя автоматически переносить в новый бенчмарк без проверки семантики.
- Адаптеры PIL, cv2 и torchvision возвращают разные типы. Наличие Tensor на выходе само по себе не гарантирует одинаковые каналы, dtype и ориентацию.
- `pyproject.toml` поддерживает Python 3.12–3.13; torch/torchvision не являются обязательными базовыми зависимостями. В локальной `.venv` установлены torch `2.10.0+cu128`, torchvision `0.25.0+cu128`.
- В рабочем дереве уже были изменения README, benchmark, CLI, тестов и скриптов. Они не являются результатом этой задачи. На этапе постановки изменяется только этот артефакт.

Проверка ImageNet: [официальный preset ResNet50](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.resnet50.html) использует resize короткой стороны до 256 для V1 или 232 для V2, затем центральный crop 224, масштабирование в float и нормализацию ImageNet. Локальный `torchvision/transforms/_presets.py:ImageClassification` подтверждает эту последовательность. Пользователь выбрал геометрию V1, но исключил нормализацию и отдельно подтвердил `uint8 [0,255]` без масштабирования. Это нагрузка подготовки батча, не полный вход ImageNet-классификатора.

В [torchvision 0.25 ToImage](https://docs.pytorch.org/vision/0.25/generated/torchvision.transforms.v2.ToImage.html) вход NumPy поддерживается без масштабирования значений. [Resize](https://docs.pytorch.org/vision/0.25/generated/torchvision.transforms.v2.Resize.html) с целым размером сохраняет пропорции и меняет короткую сторону. Локальный `torchvision/transforms/v2/functional/_type_conversion.py:to_image` использует `from_numpy`, перестановку HWC→CHW и приведение к contiguous; безопасность read-only буферов и отрицательных strides требует общей политики на границе трансформа. [OpenCV](https://docs.opencv.org/4.13.0/d8/d6a/group__imgcodecs__flags.html) предоставляет прямой RGB-режим и отдельный флаг отключения EXIF-поворота; отсутствие RGB API должно отражаться как недоступность варианта, а не скрытая замена пути.

[CenterCrop](https://docs.pytorch.org/vision/stable/generated/torchvision.transforms.v2.CenterCrop.html) дополняет маленькие изображения нулями. [Документация DataLoader](https://docs.pytorch.org/docs/2.14/data.html) описывает запуск workers при создании итератора и сохранение workers между эпохами через `persistent_workers`. Просмотренная web-версия новее локального torch; совместимость должна подтверждаться для реально поддерживаемых версий, а не ссылкой на текущую документацию.

[Документация psutil](https://psutil.io/api/) различает CPU-процент всей системы и процесса; процессный показатель может превышать 100%. Для этой задачи единицы, область наблюдения, интервалы и RSS-агрегация определены явно в R12/R13. Выбор конкретного сборщика остаётся решением планировщика.

## Желаемый результат

Пользователь запускает новый режим на каталоге изображений или использует Python API со списком файлов. Для каждого варианта ридера получает время исчерпания DataLoader, число выданных изображений и батчей, амортизированное время на изображение и пропускную способность. При включённом мониторинге видит загрузку CPU и наблюдаемое потребление памяти основного процесса и workers по тем же эпохам. Результат содержит достаточно настроек, чтобы повторить сравнение и понять ограничения наблюдений.

## Участники и сценарии

- Пользователь выбирает способ чтения изображений для последующей обработки в PyTorch.
- Разработчик адаптера сравнивает несколько содержательно разных вариантов одной библиотеки.
- Пользователь сравнивает `num_workers`, `batch_size`, shuffle и настройки очереди/жизненного цикла workers на одной машине и одном наборе файлов.
- Пользователь сопоставляет скорость с CPU и памятью, чтобы заметить рост расхода ресурсов без соответствующего выигрыша в пропускной способности.

## Область задачи

### Включено

- Самостоятельный CPU DataLoader-бенчмарк, общий датасет списка файлов и таргет `0`.
- Отдельный пакет адаптеров нового бенчмарка со стабильными именами вариантов.
- Общий опциональный пространственный трансформ `Resize(256) → CenterCrop(224)`; общий выход всегда Tensor `uint8`, без нормализации и масштабирования.
- Настройки DataLoader, полные проходы, измерения и воспроизводимые результаты.
- Опциональный мониторинг CPU/памяти относящихся к запуску процессов с наблюдениями и сводками по эпохам; выключен по умолчанию.
- Минимальный первоначальный набор ридеров, проверка ошибок и совместимости старого CLI.

### Не включено

- Forward/backward модели, обучение, GPU-декодирование, копирование на GPU, DDP.
- Автоматический подбор конфигурации, распределённые эксперименты, dashboard.
- Полноценный profiler, точный учёт пиков между сэмплами и уникальных физических страниц на всех ОС, обязательная системная телеметрия всей машины.
- Хранение декодированного датасета в памяти или новый формат хранения датасета.
- Перенос всех существующих библиотек и внешних плагинов в первой версии.
- Матрица произвольных аугментаций, float32-препроцессинг и нормализованные модельные ImageNet-presets.
- Реализация продукта в рамках текущего brainstorm; в этой стадии создаётся только задача.

## Требования

### Функциональные

- **R1 — данные:** использовать существующий сбор файлов с теми же правилами выбора N; зафиксировать список один раз на сравнение и не менять список вызывающей стороны. Python API принимает явный список путей. `0` означает все изображения; пустая выборка — явная ошибка.
- **R2 — датасет и ридеры:** map-style Dataset возвращает `(image, 0)`; ридеры находятся в отдельном пакете и выбираются по однозначному ID варианта. Первоначальный набор: PIL, torchvision CPU и cv2. Для OpenCV сравниваются два содержательно разных пути — прямой RGB decode и BGR decode с преобразованием в RGB; недоступный в установленной версии путь явно помечается недоступным. Готовый RGB ndarray отдаётся непосредственно в общий трансформ, без дополнительного round-trip или безусловной копии в адаптере. PIL приводится к RGB NumPy; готовый CPU RGB CHW Tensor torchvision поступает в общий трансформ непосредственно, без Tensor→NumPy→Tensor. Геометрия и выходной dtype не оптимизируются отдельно по библиотекам. Быстрота OpenCV-пути оценивается полным замером, а не обещанием универсально самого быстрого способа перестановки каналов.
- **R3 — общий контракт:** вход одного общего трансформа — полное исходное RGB-изображение с тремя каналами, CPU `uint8 [0,255]`: либо NumPy ndarray HWC, либо готовый Tensor CHW. Общий входной шаг приводит ndarray к Tensor и сохраняет уже совместимый Tensor без промежуточного ndarray. Затем все варианты используют одну реализацию пространственного трансформа и одинаковые параметры. Выход — обычный CPU `torch.Tensor`, `uint8 [0,255]`, CHW; при включённой геометрии форма `3×224×224`, после collation — `B×3×224×224`. Не выполнять `/255`, явное приведение изображения к float или `Normalize(mean,std)`; внутренние вычисления выбранного resize kernel не ограничиваются этим требованием к представлению. Общая граница NumPy→Tensor безопасно обрабатывает read-only, non-contiguous и отрицательные strides; необходимые копии входят в измеряемую работу и подчиняются одной политике, без ветвлений по ID ридера. Трансформ не изменяет вход и не теряет владельца буфера. Никакой гарантии zero-copy для всего пути нет.
- **R4 — трансформ:** по умолчанию применять Tensor-операции torchvision: `Resize(256, interpolation=BILINEAR, antialias=True)` короткой стороны с сохранением пропорций, затем `CenterCrop(224)`. Это зафиксированный пространственный эталон; округление размеров/координат и значений соответствует выбранной поддерживаемой версии torchvision, которая записывается в результат. Малые изображения сначала увеличиваются до короткой стороны 256, а затем обрезаются; crop-only с padding не является default. Отключение пространственного трансформа сохраняет исходные H/W, но общий Tensor-контракт R3 остаётся. Опция предназначена для одинаковых размеров при обычном stacking; несовместимые размеры в батче дают понятную ошибку без автоматического перехода к спискам/padding. `batch_size=1` позволяет читать изображения разных размеров.
- **R5 — настройки:** новый CLI-режим и Python API позволяют задавать reader, `num_workers`, `batch_size`, shuffle, seed, число эпох, `prefetch_factor`, `persistent_workers`, `pin_memory`, `drop_last`. В новом режиме `num_workers=0` означает основной процесс. Для MVP достаточно повторяемых запусков со скалярными настройками; встроенное декартово произведение конфигураций не обязательно.
- **R6 — одинаковая нагрузка:** одинаковые список, seed и номер эпохи задают одинаковый порядок индексов для сопоставимых ридеров, независимо от числа workers. Shuffle меняет порядок, а не выборку. Использовать выдачу в порядке sampler. Не требовать, чтобы случайная перестановка обязательно отличалась от предыдущей. При `drop_last=True` явно показывать отброшенное количество; разные фактически выданные подмножества не считать одинаковой нагрузкой.
- **R7 — границы времени:** Dataset и объект DataLoader создаются до таймера. Каждая измеряемая эпоха начинается непосредственно перед `iter(loader)` и заканчивается после полного исчерпания итератора. Внутри — чтение, декодирование, необходимые преобразования, трансформ, collation, доставка батчей и штатные действия итератора. Бенчмарк полностью потребляет батчи, считает изображения и не накапливает их. Импорты основного процесса, поиск файлов, подготовительные проверки и вывод отчёта находятся вне таймера. Инициализация workers, выполняемая при итерации, остаётся в измерении.
- **R8 — эпохи и кэш:** использовать один DataLoader на конфигурацию, отдельно помечать первую и последующие эпохи. Не смешивать первую эпоху с остальными в единственной итоговой средней. Полные времена всех эпох доступны; для последующих выводится медиана, а при их отсутствии — явное отсутствие значения. Предлагаемый default — 5 измеряемых эпох без скрытой прогревочной эпохи DataLoader. Прогрев байтов выбранных файлов включён по умолчанию перед каждой конфигурацией и отключаем; он вне таймера, не хранит байты датасета в Python и не обещает гарантированного состояния OS cache. Отключение прогрева не называется холодным кэшем.
- **R9 — метрики:** для каждой успешной эпохи сохранить `epoch_seconds`, фактические `images_delivered`, `batches_delivered`, `ms_per_image = 1000 * epoch_seconds / images_delivered`, `images_per_second = images_delivered / epoch_seconds`. Делитель — фактические изображения, не число батчей и не длина датасета. Нулевой результат не порождает успешные throughput-метрики. `ms_per_image` обозначает амортизированную стоимость выдачи, не latency одиночного чтения.
- **R10 — ошибки:** повреждённый файл, неподдерживаемый вход, `None` ридера, несовместимый batch и ошибка worker делают соответствующий запуск неуспешным. Нельзя молча пропускать изображение, заменять его нулями или включать неуспешную эпоху в успешную сводку. Где известны, сообщение содержит reader ID, путь и причину. Отсутствующая optional-библиотека отображается как недоступная с причиной; явный выбор недоступного ридера завершается ошибкой. В MVP скрытые fallback-декодеры запрещены.
- **R11 — результат и воспроизведение:** предоставить читаемую таблицу и структурированный результат Python API с теми же данными. Зафиксировать ID/описание пути ридера, версии backend/torch/torchvision/Python/пакета, ОС, доступные CPU, метод запуска workers, полный конфиг трансформа/DataLoader, seed, выбранное N, идентификатор упорядоченного списка файлов и номера эпох. Результат позволяет получить или сохранить точный список выбранных путей: одного хэша недостаточно для восстановления выборки. Записывать доступные настройки внутренних потоков backend/torch; неизвестные помечать явно. Для pin_memory различать запрос и фактическое закрепление, которое проверяется вне основного измерения; неприменимые или неэффективные режимы обозначаются явно. Ресурсный результат дополнительно содержит режим изоляции, baseline RSS, метод/версию сборщика, интервал и полноту наблюдений. Отдельный формат CLI-экспорта может выбрать планировщик.
- **R12 — наблюдение ресурсов:** в CLI и Python API предоставить опциональное включение CPU/памяти и положительный интервал сэмплирования; default off, предлагаемый интервал 100 мс. Наблюдать процесс-потребитель DataLoader и связанные workers/их потомков, а не только родителя и не всю машину. Каждая конфигурация с мониторингом выполняется в свежем процессе-потребителе по C7; внешний координатор/наблюдатель исключается из группы. Сторонние процессы не включаются. Идентичность процесса учитывает PID и время создания, чтобы повторное использование PID не объединяло счётчики. Сэмплы имеют монотонное время начала/конца обхода, ID конфигурации/эпохи, процессы и статус полноты. Сбор начинается до измерения; в сводку эпохи входят наблюдения соответствующего измеряемого окна. Мониторинг не добавляет ожиданий или печати на каждый batch и завершается при успехе/ошибке.
- **R13 — метрики ресурсов:** показывать среднюю наблюдаемую загрузку CPU по времени валидных интервалов и максимум интервального наблюдения, где 100% означает один логический CPU, а сумма по процессам может превышать 100%. Основа — приращения собственных user+system CPU times наблюдаемых процессов; накопленные children times родителя дополнительно не суммируются. Среднее взвешивается длительностью интервалов. Обе границы включённого CPU-интервала должны находиться внутри одной измеряемой эпохи; пересекающий границу интервал сохраняется как cross-boundary и исключается из её CPU-сводки, без пропорционального распределения. Не называть показатель load average ОС. Для памяти — RSS процесса-потребителя, сумма RSS workers и общий RSS, среднее наблюдений и наблюдаемый максимум в MiB. Общий пик — максимум суммы одного обхода sampler, не сумма индивидуальных максимумов; такой обход не является атомарным снимком, его начало/конец сохраняются. Сумма RSS может повторно учитывать shared pages и не обозначает уникальную физическую память. PSS допускается отдельным полем при доступности, обязательная метрика — RSS. Таблица и сэмплы показывают интервал, sample count, временное покрытие CPU (валидная длительность / время эпохи) и отдельно неполноту состава/счётчиков процессов. Первый CPU-отсчёт, исчезнувший процесс, ошибка доступа и слишком короткая эпоха дают missing/N/A или partial, не выдуманный ноль. Неполные значения и сводки явно помечаются; полное покрытие времени не гарантирует обнаружения каждого краткоживущего процесса.

### Качество и ограничения

- **C1 — совместимость:** существующие `benchmark`, default-вызов, `libs`, `data`, форматные адаптеры и значение старого `--nw 0` сохраняются. Новый режим не делает torch/torchvision обязательными для базовой установки; его зависимости и отсутствие этих зависимостей описаны явно, импорты ленивые.
- **C2 — жизненный цикл:** Dataset, ридеры и трансформы совместимы с `spawn`; workers предыдущей конфигурации освобождаются перед следующей, в том числе при исключении. `persistent_workers=True` при нуле workers и явно заданный prefetch при нуле workers отклоняются. Batch size, число эпох и применяемый prefetch положительные; число workers неотрицательное. Недопустимые сочетания не исправляются молча.
- **C3 — семантика изображений:** начальный гарантированный вход — обычные 8-bit RGB JPEG/PNG. Grayscale приводится к трём RGB-каналам; alpha отбрасывается без композиции; EXIF orientation не применяется; не выполнять ICC-преобразование. Вариант обязан соблюдать эти правила либо явно отказать в неподдерживаемом случае. Ограничения относятся к исходному файлу, а не только к dtype после decode: для исходных 16-bit, CMYK и многостраничных изображений MVP даёт явный отказ, даже если выбранный декодер умеет автоматически превратить их в RGB uint8. Проверка исходного режима не должна скрыто менять snapshot или включать альтернативный декодер в успешную строку. Побитовое совпадение разных JPEG-декодеров не является универсальным критерием.
- **C4 — качество измерения:** монотонный wall-clock таймер, одинаковое тело потребления батчей, без вычислений модели и подробного progress-вывода на каждый batch. Проверки содержания и индексов выполняются в тестах/проверочных запусках, а не как полное сравнение каждого изображения в основном замере. Не вводить порог ускорения как доказательство корректности.
- **C5 — разработка:** соблюдать `AGENTS.md`, Python 3.12–3.13, использовать `uv` для Python и зависимостей. Проверять поведение относительно поддерживаемой пары torch/torchvision. Существующие незакоммиченные изменения учитывать, не отменять.
- **C6 — достоверность наблюдения:** default off не запускает sampler и не требует его optional dependency. При явном включении недоступная зависимость диагностируется до замера; ошибка сбора во время замера отдельно помечает ресурсную часть как неполную, не превращая успешную итерацию в полные измерения ресурсов. Накладные расходы наблюдения не вычитаются из wall time; monitored/off и разный интервал различимы в результатах. Sampled peak не обещает поймать пик между наблюдениями; короткоживущие workers могут быть пропущены. Метод наблюдения и его известные ограничения описываются вместе с метриками.
- **C7 — сопоставимость памяти:** при включённом наблюдении каждая конфигурация получает свежий процесс-потребитель с выбранным backend, без состояния прежних конфигураций; один и тот же процесс сохраняется между её эпохами. Запуск этого процесса, его начальные импорты, создание Dataset/DataLoader и начальный RSS после этой подготовки находятся до таймера эпохи. Начальный RSS публикуется рядом с абсолютными наблюдаемыми уровнями; разность с baseline можно дать дополнительно, но она не обозначает точный объём выделений. Сэмплы мониторинга и результаты предыдущих конфигураций хранятся вне измеряемого процесса, чтобы их накопление не имитировало рост памяти DataLoader. Достаточны отдельные скалярные запуски CLI или эквивалентная изоляция вызова API; платформа экспериментов не требуется. Изоляция процесса не сбрасывает OS cache и не гарантирует одинаковую системную нагрузку.

## Рассмотренные подходы

| Подход | Работа | Преимущества | Затраты и риски |
|---|---|---|---|
| D: NumPy или готовый Tensor, затем общий Tensor-transform | NumPy преобразуется на общей входной границе; готовый Tensor используется напрямую; далее одна геометрия | Естественно использует готовые результаты ридеров, фиксирует последующую обработку | Два входных контракта; стоимость layout/copy остаётся частью результата |
| N: обязательно NumPy | Все ридеры выдают ndarray, затем один общий Tensor-transform | Простой единый интерфейс адаптеров | Для torchvision обязателен лишний переход представления; наличие дорогой копии при этом не доказано |
| P: общий путь через PIL | Все входы приводятся к PIL, одна PIL-геометрия, потом Tensor | Единый пространственный backend; перевод в Tensor после уменьшения | Другой пространственный эталон и дополнительные преобразования; не заявляется заранее более медленным |

Меньший достаточный охват — один выбранный режим с несколькими ридерами, отдельными скалярными запусками конфигураций и расширяемым пакетом адаптеров. Независимая геометрия внутри каждого ридера исключена уточнением пользователя. Полный перенос старых адаптеров и встроенная сетка экспериментов отложены. Старый бенчмарк остаётся полезным, но самостоятельно не измеряет collation и доставку батчей.

Для мониторинга рассмотрены повторное использование процесса с публикацией baseline и свежий процесс на конфигурацию. Первый вариант проще, но наследует память прежних библиотек/аллокаторов. Выбран свежий процесс для сопоставимых ресурсных замеров; его запуск находится вне времени эпохи, а baseline всё равно публикуется.

## Решение

Зафиксирована общая граница: отдельный бенчмарк реального CPU DataLoader поверх существующего списка файлов, общий смысл обработки, таргет `0`, отдельные ридеры и фактическое потребление всех батчей. Измерение заканчивается в основном процессе без вычисления модели.

Выбран D: RGB NumPy либо готовый RGB Tensor поступает в один общий входной шаг, далее одна Tensor-геометрия torchvision `Resize(256, BILINEAR, antialias=True) → CenterCrop(224)`, выход `uint8 [0,255]`. Это сохраняет требование пользователя об одинаковом трансформе и естественно использует готовый Tensor torchvision. PIL преобразуется в RGB NumPy; OpenCV получает RGB одним из явно названных путей. Обязательный Tensor→NumPy→Tensor и общий PIL round-trip не выбраны, поскольку они не нужны для данного общего Tensor-контракта; утверждений об их неизбежном проигрыше в скорости нет.

Пользователь явно подтвердил опцию без пространственного трансформа для одинаковых размеров. Обязательный Tensor-контракт остаётся. Пользователь также добавил цель наблюдать CPU/память; минимальный мониторинг включается отдельно. Для сопоставимости RAM ресурсные конфигурации изолируются свежими процессами, первая и поздние эпохи разделяются, sampling и его ограничения явно записываются.

## Техническое направление

Поток данных: зафиксированный список путей → Dataset с выбранным ридером → RGB ndarray HWC или готовый RGB Tensor CHW → общий входной шаг до Tensor → общий resize/crop либо отключённая геометрия → DataLoader/collation → потребление батчей → результат эпохи и сводка.

Новый пакет ридеров отделяет контракт изображения от текущих `img_libs`; безопасное переиспользование отдельных функций допустимо, автоматический перенос graceful wrappers и fallback — нет. Структура классов, реестра и формат экспорта остаются решениями планировщика после ревью. При мониторинге процесс-потребитель и его workers составляют измеряемую группу, внешний наблюдатель собирает её CPU/RSS по эпохам. Инициализация свежего процесса остаётся вне таймера; его память перед первой итерацией образует опубликованный baseline.

## Риски и граничные случаи

- Малые изображения увеличиваются при resize; экстремально вытянутые изображения могут дать большой промежуточный Tensor. Без пространственного трансформа размеры могут мешать stacking.
- Неподдерживаемые исходные глубина/режим могут скрыться после `convert("RGB")`: ограничения входных файлов проверяются отдельно от dtype результата. Общий сборщик может выбрать BMP/TIFF; такой файл вызывает явный отказ, а не дополнительную молчаливую фильтрацию snapshot.
- Срез `bgr[..., ::-1]` может быть дешёвым представлением с отрицательным stride, но его подготовка к Tensor требует работы. При сравнении учитывать весь путь и общую политику копирования.
- Последний неполный батч, N меньше batch size и `drop_last=True` требуют фактического подсчёта, включая ноль изображений.
- JPEG-декодеры могут давать небольшие различия пикселей; проверять семантику и контрольные изображения, не требовать универсального точного равенства.
- OS cache не управляется полностью; первая эпоха не тождественна холодному чтению, а byte warmup не прогревает все пути исполнения.
- Большие batch/prefetch/workers расходуют RAM и shared memory; ошибки ресурсов не являются успешными быстрыми замерами.
- `pin_memory=True` может быть неэффективным без поддерживаемого accelerator; фиксировать фактический исход/предупреждение, не обещать ускорение без GPU-потребителя.
- Количество внутренних потоков библиотек может менять рейтинг при одном `num_workers`; результаты относятся к записанному окружению.
- Повторное перечисление каталога и изменение файлов между запусками нарушают воспроизводимость; сохранённый manifest подтверждает пути, но не неизменность содержимого.
- RSS суммирует адресные пространства процессов с общими страницами; его рост при добавлении workers не равен такому же росту уникальной занятой RAM. Мониторинг сам расходует CPU/память, а сэмплы могут пропускать короткие пики и процессы.

## Критерии приёмки

- **AC1 (R1, R6):** на контролируемом списке Dataset выдаёт все выбранные элементы ровно один раз за эпоху при `drop_last=False`; исходный список не меняется. При одинаковых seed/эпохе фактический порядок индексов нескольких эпох совпадает между ридерами, при 0/нескольких workers, с/без persistence и в независимых повторных запусках. Проверки равенства seed недостаточно. Пустой ввод отклоняется.
- **AC2 (R2, R3, C3):** PIL, torchvision и два объявленных OpenCV-пути выбираются по отдельным ID; если API прямого RGB недоступно, это видно в списке вариантов и диагностике. Проверочный трансформ подтверждает RGB HWC ndarray или RGB CHW Tensor `uint8` на входе и одну общую Tensor-геометрию у всех вариантов; готовый совместимый RGB ndarray попадает на вход без безусловной копии в адаптере, а готовый Tensor не проходит через NumPy. Выход — CPU Tensor `uint8 [0,255]`, `3×224×224`, затем батч `B×3×224×224`. На цветовых, grayscale, alpha и EXIF-примерах соблюдается C3; контрольные постоянные значения 0, 128 и 255 сохраняются после геометрии, без `/255` и mean/std. Одинаковые заранее декодированные пиксели в ndarray/Tensor дают одинаковый результат общего трансформа. Read-only, положительно-strided non-contiguous и отрицательно-strided RGB ndarray обрабатываются общей безопасной границей с теми же результатами, что их обычные копии; источник не изменяется, время жизни буфера корректно. Torchvision-алиасы одного пути не засчитываются как разные реализации.
- **AC3 (R4):** на прямоугольном входе H=100, W=200 промежуточная геометрия — H=256, W=512, затем центральные `224×224`; квадрат `128×128` сначала увеличивается до `256×256`. На нечётных и вытянутых изображениях проверяются политика округления, расположение центральной области и неизменные параметры bilinear/antialias. Диагностические координатные/цветовые изображения проверяют геометрию независимо от вызова того же production-объекта; одной проверки финальной формы недостаточно. В режиме без геометрии выход остаётся Tensor `uint8` исходных H/W, одинаковые размеры собираются обычным stacking; смешанные несовместимые размеры дают понятную ошибку. `batch_size=1` работает с разными размерами.
- **AC4 (R5, R6, R9):** при N=10 и batch size=4 без drop_last выдаются батчи 4/4/2 и знаменатель 10; с drop_last — 4/4, знаменатель 8 и явно 2 отброшенных изображения. N<batch size с drop_last не создаёт успешных метрик на нулевом числе изображений.
- **AC5 (R7, R8, C4):** проверка границ таймера подтверждает включение создания итератора и полного исчерпания, исключение file discovery, byte warmup и отчёта. Первая эпоха отмечена отдельно; при одной эпохе отсутствует выдуманная медиана последующих. Persistence действует между эпохами одной конфигурации; его начальная стоимость не скрывается общим средним.
- **AC6 (R9, R11):** на контролируемых времени и числе изображений формулы дают ожидаемые значения. Таблица и Python-результат согласованы; доступны времена каждой эпохи, конфиг, версии, manifest/идентификатор выборки, seed, фактические N и batch count. Незавершённая эпоха не участвует в успешной сводке.
- **AC7 (R10, C3):** corrupt/unsupported файл, `None`, недоступный явно выбранный backend и worker exception завершаются явным неуспехом. Проверены BMP/TIFF в исходном snapshot и исходный 16-bit/CMYK-пример, который декодер способен автоматически привести к RGB uint8: успешное приведение не скрывает отказ по исходному формату. Нет пропущенных изображений, замены нулями или fallback под прежним именем. Диагностика содержит известный reader ID и путь.
- **AC8 (R11, C1, C2, C5):** проверочный запуск с 0 workers и с несколькими workers через `spawn` проходит на поддерживаемом окружении; несовместимые параметры отклоняются. Проверка pin_memory различает запрошенный параметр и фактический эффект, включая окружение без подходящего accelerator. После успеха/ошибки не остаются workers прежней конфигурации. Без torch/torchvision базовый импорт и старые команды сохраняют доступность, новый режим сообщает недостающие зависимости.
- **AC9 (R2, R5, R11, C1, C5):** документация показывает запуск нового режима, повтор сравнения с другим worker/batch/shuffle, смысл единиц и отличие от полного ImageNet pipeline. Старые CLI-сценарии и семантика `--nw 0` проверены регрессионными тестами. Проверки выполняются через `uv`; порог производительности не требуется.
- **AC10 (R12, R13, C6):** без мониторинга sampler не создаётся и его зависимость не требуется. С мониторингом проверочный запуск с 0 и несколькими workers даёт ресурсные поля и структурированные сэмплы по правильным эпохам. Детерминированная трасса parent/workers с разными длительностями интервалов подтверждает сумму собственных CPU times без повторного учёта children times, единицу 100%=один CPU, взвешенное среднее, RSS-сумму и максимум суммы одного обхода; индивидуальные максимумы не суммируются. Наблюдатель и несвязанные процессы исключены.
- **AC11 (R12, R13, C6):** исчезновение worker, повторное использование PID, отсутствие счётчика, первый CPU-отсчёт, эпоха короче интервала и ошибка sampler имеют явные missing/partial/N/A, не нулевые метрики. Межэпоховые CPU-интервалы исключаются из сводок с cross-boundary меткой, без пропорционального распределения. Отдельно проверяются временное coverage и неполнота процессов, включая их отражение в частичных суммах. Sampler освобождается после успеха и исключения. В таблице видны режим наблюдения, интервал, sample count и ограничения RSS/observed peak; длительность итерации не корректируется вычитанием overhead.
- **AC12 (R11, R12, C7):** две ресурсные конфигурации используют разные свежие процессы-потребители, в том числе при повторе в обратном порядке; у каждой публикуется RSS после подготовки и до первой итерации. Workers сохраняются только внутри своей конфигурации согласно persistence. Накопленные samples и предыдущие результаты не хранятся в измеряемом процессе. Проверка границ подтверждает, что запуск/импорты процесса не добавлены к `epoch_seconds`. Совпадение абсолютных RSS при смене порядка не является требованием: ОС и распределение памяти всё равно могут различаться.

## Открытые вопросы и предположения

### Блокирующие

Содержательных вопросов к пользователю нет. Q1 закрыт требованием одного общего трансформа и естественного приведения форматов; обработка готового Tensor torchvision описана явно. Q2 закрыт ответом пользователя `uint8 [0,255], без масштабирования значений`. Resize+crop без нормализации, опция без геометрии и цель наблюдать CPU/память подтверждены пользователем. Формальный переход к планированию разрешён одобренным ревью текущей ревизии, раунд 01.

### Неблокирующие

- Минимальный набор PIL/torchvision/cv2 и два OpenCV RGB-пути ограничивают первую версию. Добавление остальных backends — дальнейшее расширение; недоступность конкретного optional backend в одном окружении не отменяет требования реализовать его адаптер.
- Имя новой подкоманды предлагается `dataloader`; точные флаги и публичные имена Python API определяются при планировании, сохраняя R5/C1.
- Предлагаемые defaults для настроек: batch size 32, workers 0, shuffle false, seed 0, drop_last false, persistent_workers false, pin_memory false; prefetch None при 0 workers и 2 при workers>0; 5 эпох. Это технические предложения, не требования к оптимальной производительности.
- Формат сохранения manifest/результатов, точная пара поддерживаемых torch/torchvision и инструменты фиксации внутренних потоков — решения планировщика в пределах R11/C5.
- Механика изоляции ресурсных конфигураций, сборщик CPU/RSS и сериализация сэмплов — решения планировщика в пределах R12/R13/C6/C7. RSS обязателен для поддерживаемого мониторинга; PSS — необязательное расширение, не блокер.
- Бенчмарк измеряет максимально быстрое потребление CPU-батчей. Он не оценивает перекрытие загрузки с обработкой модели и не обещает ускорение обучения.
